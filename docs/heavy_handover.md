给 **2027 重装机器人**（编号 1，42mm / 16.5 m/s，两阶段形态）做自动瞄准后端：

## 2. 代码地图：怎么跑起来

### 2.1 构建

```bash
cd <repo>
cmake -B build
make -j$(nproc)
```

`build/calibration/`（`calibration/*.cpp`）——仓库没有设置 `RUNTIME_OUTPUT_DIRECTORY`，
这是 CMake 的默认行为。本机（Windows）**已能编译**：用 MSYS2 ucrt64 的 g++ 14.2 +
真实依赖头文件（OpenCV 4.12 / Eigen 3.4 / fmt 11.2）可以编 `tasks/auto_aim/` 的全部

## 5. 已修的关键 bug（**别再踩一遍**）

每一条都是"现象看着像算法 bug，实际是别的问题"。

### 5.1 弹道补角语义：h≠0 的目标系统性打低（最隐蔽）

- **现象**：水平 2 m、抬高 2 m 的靶子完全打不中；平射正常。
- **根因**：`ballistic-main` 的 CSV 里 `pitch` 列是**相对视线的补偿量**，不是绝对仰角
  （`g.py`: `Pitch = degrees(solved_pitch − atan2(Y,X))`）。运行时没加 `atan2(h,d)`。
- **数值**：d=2/h=2 应 46.23°，实际给 1.23°。
- **为什么很久没发现**：`h=0` 时 `atan2(0,d)=0`，**这个 bug 在平射上完全不可见**，
  而当时的对照测试只在 h=0 上做。
- **修法 + 防回归**：`solve()` 内部加视线仰角；`ballistics_poly_check.cpp` 第 3 节
  强制覆盖 `h ∈ {−1.9,−1.0,0,1.0,1.9,2.0}`。
- **教训**：**任何"只在零位成立"的验证都是假验证**。

### 5.2 阻力系数 0.2415（12.9 倍）

- **现象**：8 m 以上弹道无解，云台不受控。
- **根因**：`sentry.yaml` 的 `drag_coefficient_up=0.2415` 与 22 m/s 不自洽
  （17mm 物理值 0.01875）→ 解算抛异常 → `plan.control=false`。
- **修法**：该链路已整体删除，改为 `kDefaultDragCoefficient=0.01875` + 多项式表。
- **注意**：42mm 的物理 k ≈ **0.00513**，回退路径要按弹种选。

### 5.3 ±π 二义性导致关联锁死（`armor_id` 恒 0）

- **现象**：旋转目标 `armor_id` 一直 0，`a` 锯齿，`w` 在 ±0.4 摆动。
- **根因**：关联用 `min(|yaw_err|, |yaw_err±π|)`，使 0↔2、1↔3 等价 → 永远匹配 0 号板。
- **修法**：用板的几何法向消歧（`n̂·p>0` 则 `+π`），删除 flip 分支。
- **验证**：`python -m rdbg metrics` 看 `armor_id` 是否 0→1→2→3 推进、`w` 过零次数。

### 5.4 观测窗红框乱飘（三处叠加）

① `debug_xyza` 在 `get_trajectory()` 循环里被覆写成"未来时刻"；② 跨线程无锁撕裂读；
③ 失败路径残留旧值。修法：只写最终值 + mutex + 失败清零。

### 5.5 低置信度框产生"幽灵板"

- **现象**：`d=0.30 m` 的脏解，poly 报"超出拟合范围"。
- **根因**：远距离低噪声角点 → PnP 解出几十米/NaN；`r/l/h` 在 Q 里无过程噪声，污染不可逆。
- **修法**：`min_valid_dist=0.5`、`diverged()` 加"中心过近"判据、planner 过滤。
- **教训**：**EKF 前的闸门比 EKF 里的鲁棒性更重要**。

### 5.6 指标定义错（w 的"差分变号次数"）

- 白噪声的差分变号率恒 ≈50%，用它判"抖"是错的。改为 **`w` 过零次数/秒**
  （good 0.0/s，bad 13.4/s）。

### 5.7 工具链坑（不是代码 bug，但会让你浪费一天）

| 坑 | 表现 | 对策 |
|---|---|---|
| 写文件时 `\n` 被吃掉一层 | C++ 字符串里出现真实换行 → `missing terminating "` | 用 `puts` 或多段输出，**避免在补丁里写转义** |
| PowerShell 里反引号是转义符 | 脚本静默失败/字符串被吃 | 脚本内容用单引号 here-string，或 `chr(96)` 构造 |
| 控制台 GBK | 打印 UTF-8 中文乱码 | 写文件后读，别信控制台显示 |
| `git push` 时 SSH-over-443 不稳 | `kex_exchange_identification` / timeout | 重试；或改 HTTPS + 凭据缓存 |
| heredoc 太长被截断 | `here-document delimited by end-of-file` | 分段落盘 |

## 6.5 未来方向（已决策：暂不实现）

> 这些是"想清楚了但先不做"的事。记在这里是为了**不丢信息**，也为了避免
> 下次有人（包括我自己）重新推导一遍。

### F1 · 热量预算下的开火时机决策

**现状**：`center_aimer` 的热量闸是"**能打就打**"——第一个满足
`in_window && settled && heat_ok` 的窗口立刻开火。

**问题**：这个策略在高速自转下会浪费热量。实测（w=5 rad/s、5 秒）：

```
可用窗口 17 个
热量只允许 7 发
-> 约 60% 的窗口被热量挡掉，且挡掉的是"后面"的窗口，不是"最差"的窗口
```

也就是说，现在会**在第一个窗口就打掉一发**，哪怕后面有更正对、更近、
命中率更高的窗口。

**未来要做的**：给窗口打分的**时机决策层**，在热量受限时挑最优窗口：

| 可用的打分因子 | 数据来源 | 说明 |
|---|---|---|
| 板面正对程度 | `cos_face` | 已算出，越大越好（投影宽、PnP 准） |
| 对齐余量 | `hit_window/2 - align_err` | 越大越"稳" |
| 目标距离 | `aim_xyz.norm()` | 越近，弹道误差与飞行时间越小 |
| 剩余热量 | `heat_q1` vs `Q0` | 热量富余时才值得挑，快锁死时见好就收 |
| 距离下次窗口的间隔 | `t_to_cross` + `w` | 若是"马上还有机会"，可以等 |

**为什么先不做**：

1. **缺实测数据**——不知道真实比赛里目标转速分布、窗口密度，
   凭猜测定的打分权重很可能反过来伤命中率。
2. **现在是"能打就打"，行为可预测**；加了策略层后如果权重没调好，
   会出现"明明能打却不打"的诡异行为，比浪费热量更难排查。
3. 热量只在高转速下才成为瓶颈（w=1 rad/s 时 7.2 秒内热量根本没挡过），
   而高转速下的命中率本来就低，优先该做的是**降低高转速下的误差**，
   不是"挑窗口"。

**触发条件**（满足其一再动手）：

- 实车 `.rlog` 显示**热量成为实际瓶颈**（`heavy_heat_ok=0` 占比 >30%）
- 或者实测发现"挑窗口"确实能提升命中率（需要一个可控转速的靶架做 A/B）

**实现位置（预留）**：`CenterAimResult` 里已经有决策所需的全部量
（`cos_face` / `align_err_deg` / `hit_window_deg` / `heat_q1` / `t_to_cross`），
所以这层可以**完全写在 `center_aimer` 之外**，不影响现有判据。

### F2 · 闭环仿真测试台（无硬件验证命中率）

**动机**：现有测试都是**单点**验证——`center_aimer_check` 直接喂一个合成 `Target`，
跳过了 PnP 和 Tracker。所以下面这些问题的答案目前全靠推：

- h=10cm、板高排布不规则时，4 块板到底能打中几块？
- 0.5 px 的关键点噪声 → 多大距离误差 → 多少毫米落点误差？
- 热量闸真的会在高速自转下限制射速吗？限制后命中率掉多少？
- 云台一阶滞后 20/40/80 ms 各会让命中率掉多少？

闭环仿真能把这些**在无硬件条件下量化**，而且参数可以扫。

**最大的有利条件**：`Solver::reproject_armor()` 就是现成的**虚拟检测器**，
它与 `Solver::solve()` 用的是**同一套** `armor_geometry()` 与倾角，
所以「世界 → 像素 → PnP → 世界」可以精确闭环。相机内参直接用 yaml 里的实车参数
（`fx≈1818, cx≈751`），于是「1 px 噪声 → 多少米距离误差」与实车一致——
这是仿真最有价值的地方。

```
真值目标(位置/相位/转速)                    ← 仿真侧
        │
        ├─① 虚拟相机：solver.reproject_armor() → 4 像素点
        │      + 高斯噪声(0.3~1 px) + 按概率丢帧
        ↓
    ② Armor{points, color, name, type}
        ↓
    ③ tracker.track(armors, t) → Target      ← 真代码
        ↓
    ④ center_aimer.solve(...) → 指令角 + fire ← 真代码
        ↓
    ⑤ 云台动力学(一阶滞后 K/T + 纯延迟 L) → 反馈角  ← 仿真侧
        ↓
    ⑥ 弹道积分 + 击打判定 → 命中/未命中        ← 仿真侧
        ↓
   统计：命中率 / 每发代价 / 热量曲线
```

#### 必须先改一处（否则仿真测的不是生产代码）

`heavy_aim.cpp` 的 `main` 直接依赖 `io::Gimbal` / `io::Camera` / `YOLO`，
三者分别需要串口、相机 SDK、OpenVINO，**仿真里一个都实例化不了**。两个选择：

| 方案 | 结果 |
|---|---|
| A：仿真里再抄一份循环 | 成型快，但仿真测的是"另一套循环"，会与生产代码漂移 |
| **B：把决策逻辑抽成 `HeavyAimer`（推荐）** | 仿真与生产共用同一套逻辑；顺带让这段逻辑有了单测 |

抽出来的就三件事：`take_over` 判断、`bullet_speed` 兜底、`no_gimbal` 的
"指令当反馈"处理（约 50~60 行）。**纯搬移、不改行为**，抽完 `center_aimer_check`
应照样全绿。这三段依赖都不沾硬件（`io/command.hpp` 是纯结构体）。

#### 建议改两处

| 项 | 为什么 |
|---|---|
| 新增 `configs/sim.yaml` | 仿真不该写 `.rlog`/发 UDP（`enable_remote/local: false`）；同时给仿真独立参数，改噪声/转速不用动 `sentry.yaml`。**不新建的话每跑一次都会往 `logs/` 写文件** |
| 在 `tests/algo/` 加仿真入口 | `auto_executables.cmake` 会自动编成同名可执行文件，tests 已链 `tools io auto_aim`，**不用改 CMake** |

#### 不用改的地方

| 依赖 | 状态 |
|---|---|
| 虚拟检测器 | `Solver::reproject_armor()` 现成，与 PnP 同源 |
| PnP / 坐标链 | `Solver::solve()` 直接可用，只需 `set_R_gimbal2world()` 喂仿真姿态 |
| EKF / 关联 / 状态机 | `Tracker` 直接可用，参数从 yaml 读 |
| 判据 / 热量 | `CenterAimer` 直接可用（记得 `reset_heat()`） |
| 弹道 | `tools::Trajectory` 可算；击打判定另写独立 RK4，顺带当交叉验证 |

#### 三个已知的坑（踩过两个）

1. **`Armor` 必须给满 4 个关键点**——构造函数按下标取，空 vector 直接段错误
2. **`armor.color` 必须等于 yaml 的 `enemy_color`**——否则 `Tracker::track` 首行
   `remove_if` 把观测全滤掉，表现为"永远无目标"
3. **`Tracker` 要连续 `min_detect_count` 帧才建目标**（sentry.yaml 是 5），
   前 5 帧必然无目标，不要误判成丢目标

#### 仿真**测不到**的东西（必须说清楚）

| 测不到 | 原因 |
|---|---|
| 检测模型本身 | 虚拟检测器是几何投影，没有 YOLO |
| 真实 PnP 噪声分布 | 只能假设高斯；真实是厚尾（越远越差） |
| 相机曝光时序 / 传输延迟 | 仿真时间是理想化的 |
| 实车云台整定 | 只能给假定的 `(K, T, L)`，而这正是**未标定**的量 |
| `launch_delay` | 同上，仿真里只能填假设值 |

**所以定位是**：验证**逻辑正确性与参数敏感性**（能不能打到、热量会不会锁机构、
窗口密度够不够），**不能代替实车标定**。

#### 工作量

| 部分 | 规模 |
|---|---|
| 抽 `HeavyAimer`（方案 B） | ~60 行搬移 + 改 `heavy_aim.cpp` 调用 |
| 闭环仿真 `tests/algo/heavy_sim.cpp` | ~400–500 行 |
| `configs/sim.yaml` | ~30 行 |

**触发条件**：需要在无硬件时回答上面那四个问题中任意一个；或实车调试成本
明显高于仿真成本时（例如需要扫云台滞后/噪声的参数空间）。

## 7. 六个月研发计划

> 每月一个阶段，**每阶段有验收 gate，不达标不进入下一阶段**（gate 定义见
> `docs/heavy_aim_baseline.md` §7）。

### M1（第 1 月）：配置与数据基础

**交付**

1. `assets/ballistic/big.csv` 补 **V=16.5**（顺带 16.0/17.0 便于插值）
2. 弹速兜底 / 弹道表 / 回退 `k` 三项**配置化**；新建 `configs/heavy.yaml`
3. `ekf.heavy` 段 + `Tracker` 重装分支
4. 用 `eval_record` 采**第一批重装数据**（静态多角度 + 旋转靶车）
5. 建立**离线回归基线**：固定数据集 + 指标快照（`rdbg metrics`）

**Gate**：`ballistics_poly_check` 全绿（含 V=16.5、h≠0）；`heavy.yaml` 跑通 `auto_aim_debug_mpc`；
离线指标快照入库。

**风险**：重装车未必随时可用 → 先用步兵车验证配置框架，几何参数留占位。

### M2（第 2 月）：执行器辨识与 MPC

**交付**

1. 阶跃/扫频标定程序（**已有激励基础**：`tests/io/gimbal_response_test.cpp` 能注入三角波/正弦，
   缺的是**自动拟合分析**）
2. 每轴每形态 `(K, T, L, α_max)` 入 yaml（4 组：步兵/哨兵/重装未装/重装已装）
3. MPC 加执行器滞后（三阶状态或一阶补偿）；`max_*_acc` 按形态
4. 打通前馈（`*_acc` 下发或明确电控侧用法）、去掉 `distance=3.0f` 硬编码

**Gate**：阶跃超调 ≤10%；跟踪残差 ≤1.5 mrad；移动靶（匀速 2 m/s）命中率 ≥60%。

### M3（第 3 月）：多帧优化（BA）与距离精度

**交付**

1. 滑动窗口（N=5–10）重投影优化，初值取 EKF 先验
2. `σ_d` 对比实验：单帧 vs BA（目标 ≤0.09 m @8 m）
3. 侧向板 R 自适应

**Gate**：重投影 RMS ≤0.5 px；距离误差 ≤0.1 m @8 m；12 m 处不再"系统性偏低"。

### M4（第 4 月）：开火判定与板面选点

**交付**

1. 开火判据改为实测云台角 + 弹道误差投影到板面 + 动态阈值
2. 输出板上偏移 `(u,v)`；优先未加固区（×1.5）
3. 离线"若开火是否命中"评估器（ROC 扫阈值）

**Gate**：开火时预测命中概率 ≥0.8；空放率 ≤10%；单发命中率提升可量化。

### M5（第 5 月）：鲁棒性

**交付**

1. 多目标航迹管理（匈牙利 + ID 稳定）
2. 遮挡处理（缺板降权）、负样本抑制（空中机器人/场地灯）
3. 光照/曝光自适应（过曝静默已有实测证据）
4. 长跑自检（零位漂移、齿隙、热漂移）

**Gate**：30 min 无崩、P99 ≤16.7 ms、回放可复现、多目标不串号。

### M6（第 6 月）：命中率冲刺

**交付**

1. 分距离/角度/运动状态的分层统计（每桶 ≥300 发）
2. 参数冻结与最终配置
3. 交接补充文档

**Gate**：**总体 ≥75%**，各桶 ≥65%，报告带 95% 置信区间。

### 阶段依赖图

```
M1 配置基础 ──┬─→ M2 执行器/MPC ──┐
              │                    ├─→ M6 命中率
              ├─→ M3 BA/距离 ──────┤
              └─→ M4 开火/选点 ────┘
                        M5 鲁棒性 ──┘
```

1. **不能破坏步兵路径**：这个分支改的是共用文件（`planner/aimer/tracker/solver`），

3. **每改一处算法，配一个可复现验证**（U/O/B/F 四层，见基线文档 §3）。
4. **数值改动必须留证据**：改了阈值/参数，提交信息里写"改前 X → 改后 Y（依据）"。

一个任务算完成，必须同时满足：

- [ ] 代码合并到 `feat/heavy-aim`

- [ ] 提交信息含现象/根因/证据

## 附录 C：一句话总结
