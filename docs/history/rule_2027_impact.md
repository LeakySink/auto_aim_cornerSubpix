## 5. 后勤系数 λ 与图传分辨率降级（**修正：与自瞄视觉输入无关**）

> ⚠️ **本节结论已在复核后更正**。此前把 `rmuc_D-009/010` 的"图传分辨率按 λ² 降级"列为"对视觉输入影响很大"的 P1 项，属于**概念误读**——图传是给**操作手**看的画面，不是视觉算法的输入。保留本节并改写，用于记录该结论与真正受影响的链路。

### 规则原文要点
- `rmuc_D-009`（新增，5.6.1）：后勤系数 `λ = 1 − Δ/20000`（Δ = 己方基地已损失血量，基地血量上限 10000 → **λ ∈ [0.5, 1]**）。表中各项原参数以 x 代指：复活读条 = x/λ、补给区回血速率 = x·λ、远程兑换回血比例 = x·λ、**机器人交互数据带宽 = x·λ**、**图传画面分辨率 = x·λ²**。
- `rmuc_D-010`（新增，5.6.1）：x = 1920×1080；降级方式为"按面积平均降采样 + 双线性放大"，**官方选手端与自定义终端都会降级**，"原选手端 UI 清晰度不受影响"；λ=0.5 时相当于 960×540 清晰度（图 5-16 给出 λ=1/0.75/0.5 的清晰度示意）。

### 为什么与自瞄无关
1. **"图传画面"的规则定义**：`rmuc_D-010` 注释明确"图传画面分辨率包含官方选手端与自定义终端的图传画面"——即**机器人相机 → 操作间接收端**的这条下行链路，服务对象是操作手（第一视角观察与瞄准参考），而不是机载算法。
2. **本仓视觉取流是机载相机直连**：`src/standard.cpp:41` 用 `io::Camera camera(config_path);` 取流，实现位于 `io/hikrobot`、`io/mindvision`、`io/usbcamera`——工业相机/USB 相机**物理直连计算平台**，与图传链路是两条独立通道。图传被降采样/放大，不会经过 `detect()` 的输入 Mat。
3. 因此规则里"图传变糊"对**本仓（机载自瞄）**不产生任何代码侧改动；`configs/standard3.yaml` 的 ROI、`min_lightbar_length`、相机内参照旧工作。

### 真正会被 λ 影响的部分（与本仓关系有限，供参考）
| 受影响的规则项 | 影响对象 | 与本仓的关系 |
|---|---|---|
| 图传画面分辨率 = x·λ² | **操作手**的 FPV 观察质量；把识别/推流做在**自定义终端**上的队伍 | ❌ 无关。本仓不消费图传 |
| 机器人交互数据带宽 = x·λ | **多机通信**（裁判系统串口中机器人间交互数据） | ⚠️ 间接。若日后把 `tasks/omniperception` / `io/ros2` 的数据做成哨兵↔步兵、雷达↔步兵的跨机交换，需按 λ 最低 50% 带宽设计降级策略（当前本仓自瞄不依赖） |
| 热量超限惩罚：`rmuc_C-014` 提及"超 Q0 断图传"（2027 RMUL 中 `rmul_A-045` 把"可视度降低"改为"图传画面断开"） | 操作手画面被切断，发射机构锁定 | ❌ 与本仓算法无关；仅操作手须知 |

### 仍值得关注（但**不是**规则驱动，属既有技术债）
- `tasks/auto_aim/tracker.cpp:74,139` 把图像中心硬编码为 `(1440/2, 1080/2)`，而 `configs/standard3.yaml:88-89` 的内参也是按 1440×1080 标定——代码里原就带 `// TODO`。若本赛季更换相机或改分辨率，这里依然会错，建议顺手改成从图像 `cols/rows` 取中心、内参按分辨率档位加载。这与 λ 无关，只是同一片代码的遗留问题。

> 行动建议（修正后）：**无需**为 λ 做任何识别鲁棒性测试或分辨率联动改造。若队伍另有"自定义终端上跑识别"的方案，那才需要按 λ→0.5（960×540 等效清晰度）评估，但那是终端侧代码，不在本仓。
