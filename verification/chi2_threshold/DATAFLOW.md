## 2. 在卡尔曼滤波中的作用

### 2.1 它是"一致性自检"，不是滤波环节

一次 `update()` 里卡方检验的位置：

```
predict(F,Q)  →  x⁻, P⁻
                   │
                   ├─ S = H P⁻ Hᵀ + R  ──→  K = P⁻ Hᵀ S⁻¹  ──→  x⁺ = x⁻ + K v   （主链，输出状态）
                   │
                   └─ v = z − h(x⁻)  ──→  NIS = vᵀ S⁻¹ v  ──→  NIS > 9.488 ?    （旁路，只判定）
```

**没有任何一条路径从检验支路回到主链。** 因此：

- 阈值取错 **不会** 让滤波数值变差。新旧两个 EKF 同喂 300×1200 帧数据，逐帧 `max|x_new − x_old| = 2.6e-11`、`max|P_new − P_old| = 7.8e-11`，差异全部来自 LDLT 与显式求逆的浮点舍入。
- 阈值取错的后果 100% 体现在**判据失效**：要么把正常目标判死，要么对真实异常视而不见。

### 2.2 为什么必须用"先验"量

新息 `v = z − h(x⁻)` 的协方差恰好是 `S = H P⁻Hᵀ + R`，所以

```
NIS = vᵀ S⁻¹ v  ~  χ²(观测维数) = χ²(4)
```

若改用更新后的 `x⁺ / P⁺`（后验残差 + 后验 S），残差已被本次更新吸收掉一部分，统计量不再服从卡方：实测期望只有 3.3~3.7（应为 4），阈值 9.488 的实际误报率降到 2%~4%，且对目标跳变、装甲板误匹配**不敏感**——即失去了它存在的意义。

这是上一轮修正的核心：把卡方检验移到 `x`/`P` 更新之前，用先验新息 + 先验 S。

### 2.3 NIS 与 NEES 的地位不对等

- **NIS**：自由度 = 观测维数 4，无需真值即可计算，**唯一可用的一致性判据**。
- **NEES**：标准定义 `(x⁺ − x_true)ᵀ P⁺⁻¹ (x⁺ − x_true) ~ χ²(11)` 需要真值，不可得。代码里用状态修正量 `(x⁺ − x⁻)ᵀ P⁺⁻¹ (x⁺ − x⁻)` 代替，其协方差是 `P⁻ − P⁺`（秩 ≤ 4），**不服从 χ²(11)**。实测 99.9% 的爆表帧（1080/1081）源于 yaw 跨越 ±π 时 `x_add` 回绕产生约 2π 的伪跳变。
  所以 19.675 只能算保守上限，且 `nees_fail` **不被任何逻辑消费**，仅进日志。

## 3. 影响数据流

### 3.1 逐级链路

```
① EKF::update()  每帧产出 nis，与 9.488 比较 → nis_fail ∈ {0,1}
        │
        ├─ 压入 recent_nis_failures（deque，容量 window_size = 10000）
        │
② tracker.cpp:104  Σ recent_nis_failures >= 0.4 * 10000 = 4000 ?
        │
        ├─ 否 → 继续跟踪
        └─ 是 → [Tracker] Bad Converge Found!
                    → state_ = "lost"（tracker.cpp:108-109）
                    → return {}（tracker.cpp:118）
                    → 本帧无目标 → aimer 无解算目标 → 不输出射击指令
                    → 下一帧走 set_target()，用 P₀ 重新初始化一个 EKF
```

### 3.2 只读旁路（不参与逻辑）

```
data["nis"] / data["nis_fail"] / data["nees_fail"] / data["recent_nis_failures"]
        └→ src/mt_auto_aim_debug.cpp:151-155
           src/sentry_debug.cpp:169-173
           src/uav_debug.cpp:148-152
           tests/algo/auto_aim_test.cpp:181-185
        └→ RemoteLogger 上报，用于调参与离线分析
```

注意 `data["recent_nis_failures"]` 存的是**失败率**（`recent_rate`），而 `recent_nis_failures` 成员本身是 0/1 序列——两者同名不同义，读代码时容易混淆。

### 3.3 触发的必然性：滑窗把单帧误报率放大

判据等价于"窗口内失败率 ≥ 40%"。设单帧误报率为 p，则期望触发帧数 ≈ `4000 / p`：

| 阈值 | 单帧误报率 p | 期望触发帧数 | 实测触发帧数 | 60fps 下的时间 |
|---|---|---|---|---|
| 0.711（旧） | 0.926 ~ 0.943 | ≈ 4274 | **4208 ~ 4324（中位 4265）** | **约 71 秒** |
| 9.488（新） | 0.0505 | 79208 ≫ 窗口 | 5200 帧内 0 次 | 不触发 |

p > 0.4 时触发是**确定性事件**而非概率事件：窗口内失败数的标准差 `√(10000·p·(1−p)) ≈ 25`，偏离 4000 达 160σ。

## 4. 阈值取值的依据

χ²(4) 的生存函数有闭式 `P(X > x) = e^(−x/2)·(1 + x/2)`，无需任何库即可验算：

| 量 | 值 | 说明 |
|---|---|---|
| χ²(4) CDF(0.711) | 0.050034 | 0.711 是 **5% 分位数**（不是 50%，50% 分位数是 3.3567） |
| χ²(4) 95% 分位数 | 9.4877 | 代码取 9.488，名义误报率 5.00% |
| χ²(11) 95% 分位数 | 19.6751 | 代码取 19.675，但 NEES 不服从该分布（见 2.3） |

修正后用真实模型（抄 `target.cpp` 的 h / h_jacobian / F / Q / R_dig，配置取 `standard3.yaml`）跑 300×1000 帧：

```
E[NIS] = 4.0021   （χ²(4) 理论均值 4）
P(NIS > 9.488) = 5.05%   （理论 5%）
```

→ **9.488 现在严格对应 5% 显著性水平**，阈值与统计量互为充要。

## 5. 待处理项

1. **`window_size = 10000` 偏大**：60fps 下窗口长 167 秒。真实发生目标切换 / 误匹配后，脏数据要在窗口里滞留近 3 分钟才被挤出，期间 `Σ` 持续偏高。建议按帧率折算到 1~2 秒（60~120）。
2. **窗口未满时的判据偏保守**：`tracker.cpp` 用固定的 `0.4 * window_size` 而非 `0.4 * recent_nis_failures.size()`，所以前 4000 帧不可能触发；好处是冷启动安全，坏处是"刚初始化 4000 帧内的异常一律放过"。
3. **NIS 未做门控（gating）**：目前只统计不拦截。既然统计量已经可信，可以考虑对 `NIS > 9.488` 的帧**跳过本次更新**（或放大 R 后再更新），这样误匹配装甲板不会污染状态——这才是卡方检验在跟踪系统里最常见的用法，当前实现只用了它的"计数"功能。
4. **四个参数全部硬编码**，调参需重新编译，不具备实车在线调试能力。
